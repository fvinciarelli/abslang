This page walks through a real ABS document — a refund request — so you can see everything ABS can do in one place.

## The scenario

A customer returns a damaged item. The agent must verify eligibility by calling two APIs, process the refund, and confirm — with empathy, accuracy, and without deflecting. Every step is evaluated.

## Step 1: The session — pure description

Every ABS document starts with a `session` name and a `behaviors` list. Here's the full interaction before adding any evaluations:

```yaml
session: Refund request — approved
behaviors:
  - actor: user
    action: says
    content: "I want to return order #8291, it arrived damaged"

  - actor: assistant
    action: asks
    content: "I'm sorry about that. Can you confirm your name and order date?"

  - actor: user
    action: says
    content: "Franco Vinciarelli, ordered last Tuesday"

  - actor: assistant
    action: calls
    target: Orders API
    with:
      orderId: "8291"

  - actor: tool
    action: responds
    target: Orders API
    content:
      orderId: "8291"
      status: "delivered"
      eligibleForRefund: true

  - actor: assistant
    action: calls
    target: Refunds API
    with:
      orderId: "8291"
      reason: "damaged"

  - actor: tool
    action: responds
    target: Refunds API
    content:
      refundId: "R-5512"
      amount: 47.50
      status: "processed"

  - actor: assistant
    action: informs
    content: "Refund of €47.50 processed, Franco. You'll receive it in 3-5 days. Your refund ID is R-5512."
```

## Step 2: Capture values for reuse

Variables let you capture values from the conversation and reuse them later — and check they stay consistent:

```yaml
  - actor: user
    action: says
    content: "Franco Vinciarelli, ordered last Tuesday"
    capture:
      customerName: "Franco Vinciarelli"    # ← captured here

  # ... later ...
  - actor: assistant
    action: informs
    content: "Refund of €47.50 processed, Franco. Refund ID: R-5512."
    capture:
      refundId: "R-5512"                    # ← captured for consistency check
```

## Step 3: Step-level evaluations

Add `evaluations` to any Behavior to check it. Here we use `llm_judge` with multi-criteria rubrics on the assistant's responses, and `contains` for a hard fact:

```yaml
  - actor: assistant
    action: asks
    content: "I'm sorry about that. Can you confirm your name and order date?"
    evaluations:
      - type: llm_judge
        criteria: |
          1. Shows empathy for the damaged item
          2. References the order number #8291
          3. Asks for verification info before taking action

  # ... and on the final response ...
  - actor: assistant
    action: informs
    content: "Refund of €47.50 processed, Franco. You'll receive it in 3-5 days. Your refund ID is R-5512."
    capture:
      refundId: "R-5512"
    evaluations:
      - type: contains
        value: "R-5512"                     # hard fact — must include the refund ID
      - type: llm_judge
        criteria: |
          1. States the refund amount (€47.50) and timeline (3-5 days)
          2. Provides the refund reference R-5512
          3. Uses the customer's name (Franco)
          4. Reassuring tone — no upsells, no deflections
```

## Step 4: Chain evaluations — the full trace

Step-level checks verify individual responses. Chain evaluations verify the **whole conversation** — ordering, consistency, and invariants:

```yaml
evaluations:
  - type: sequence
    order:
      - { actor: assistant, action: asks }
      - { actor: assistant, action: calls, target: "Orders API" }
      - { actor: assistant, action: calls, target: "Refunds API" }
      - { actor: assistant, action: informs }

  - type: variable_consistency
    variable: refundId
    # Ensures R-5512 is the same everywhere it appears — catches hallucinated IDs

  - type: never
    match: { actor: assistant, action: hands_off }
    # This flow must resolve — no escalating to a human
```

## What this example demonstrates

| Capability | How it's used |
|---|---|
| **Step-level LLM judge** | Two `llm_judge` evaluations with 3–4 criteria each: empathy, accuracy, tone, omission |
| **Step-level exact check** | `contains: "R-5512"` — the refund ID must appear verbatim |
| **Chain sequence** | The 4 assistant actions must occur in that exact relative order |
| **Variable consistency** | `refundId` captured once, chain-checked everywhere |
| **Tool round-trips** | Two `calls` → `responds` pairs, each independently assertable |
| **Invariant guard** | `never hands_off` — the agent must resolve, not escalate |
| **Variables** | `customerName` captured from user input, reusable throughout |
