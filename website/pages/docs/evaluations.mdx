Evaluations are what make an ABS document executable as a test. Without them, a document is purely descriptive. With them, the same document can drive automated verification in CI.

## Step-level evaluations

Attached to a single Behavior. They check that Behavior's output in isolation:

```yaml
- actor: assistant
  action: informs
  content: "Your order is on the way"
  evaluations:
    - contains: "order"
    - not_contains: "error"
```

### Built-in step evaluators

| Evaluator | What it checks |
|---|---|
| `exact_match` | Content equals expected string exactly. |
| `contains` | Content includes the expected substring. |
| `not_contains` | Content does NOT include the substring. |
| `regex` | Content matches a regular expression. |
| `schema` | Content validates against a JSON Schema. |
| `llm_judge` | An LLM evaluates the content against a rubric. |

## Session-level evaluations

Placed at the top level of the document. They check properties of the whole trace:

```yaml
session: Order flow
behaviors:
  # ... behaviors ...

evaluations:
  - sequence:
      - action: calls
        target: Order MCP
      - action: informs
  - never:
      action: hands_off
```

### Built-in session evaluators

| Evaluator | What it checks |
|---|---|
| `sequence` | Behaviors appear in the expected order. |
| `never` | A behavior pattern never occurs. |
| `eventually` | A behavior pattern eventually happens. |
| `variable_consistent` | A captured variable keeps the same value across references. |

## Design decision

Step-level and session-level evaluations were deliberately kept separate — they answer different questions. Step-level asks "did this Behavior produce the right output?" Session-level asks "did the overall conversation follow the right flow?" A single evaluator trying to do both would be harder to read and harder to implement.
